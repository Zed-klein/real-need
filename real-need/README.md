# real-need

`real-need` 是一个用于需求澄清的 Codex Skill。

它在方案设计、技术讨论或项目执行之前，判断用户提出的想法是否模糊、发散或缺少结构；如果需求层还不清楚，就通过分轮追问、检验和收敛，帮助用户明确真正想解决的问题、目标、边界、价值、重要约束与成功标准，最后形成一份由用户确认的《真实需求清单》。

它不会替用户决定目标，也不会在需求尚未确认时直接进入技术方案或执行。

## 为什么需要 real-need

很多项目的返工并不是因为执行能力不足，而是因为方案开始得太早：

- 用户提出的是一个做法，但真正要解决的问题还没有说清楚；
- 想法包含多个目标，却没有区分主次；
- 范围不断扩大，临时想到的内容逐渐改变原来的方向；
- 事实、自身感受、效果预测和未知事项混在一起；
- 用户只有看到结果后，才发现自己真正重视的偏好；
- AI 过早给出方案，让未确认的假设进入后续设计。

`real-need` 把需求澄清单独放在方案讨论之前。它不要求用户一开始就知道完整答案，而是通过连续对话，帮助用户逐步发现、检验并确认自己的真实需求。

## 与普通追问的区别

普通追问往往根据上一句话继续发问，容易出现问题堆叠、前置条件未解决、重复询问或过早讨论细节。

`real-need` 将对话维护成一棵需求决策树：

- 每个问题都是一个需要确认的判断；
- 只有前置条件已经解决的问题，才进入当前轮；
- 用户回答后，AI 会更新已确认内容、未知项和依赖关系；
- 上游目标发生变化时，受影响的下游结论会重新打开；
- 不会影响需求判断的实现细节，被明确留到后续方案阶段；
- 对话只有在目标和边界清楚、关键未知及其影响被明确后才会收敛。

因此，它关注的不只是“多问几个问题”，而是让每轮问题都有依赖关系、判断用途和明确的结束条件。

## 适用场景

当用户的表达出现以下情况时，`real-need` 可以介入：

- 只有愿望、方向或做法，没有说清要解决的问题；
- 同时存在多个目标、对象、场景或方向，优先级不明；
- 使用“做一个系统”“建立知识库”“提高效率”等宽泛表达，缺少范围或结果；
- 目标与做法的关系不明确；
- 存在前后矛盾、隐含假设或明显发散；
- 缺少会影响方案的服务对象、边界、重要约束或成功标准；
- 用户希望先想清楚真实需求、整理想法或接受严格追问。

以下情况通常不需要使用：

- 目标、对象、范围、重要约束和成功标准已经明确，只需讨论实现方案；
- 用户只需要改写、总结、翻译或格式整理；
- 用户已经理解并接受现有假设，明确要求继续，且不存在会改变方向的冲突。

缺少普通实现细节并不代表需求模糊。只要需求层足以支持后续讨论，`real-need` 就不会为了追问而追问。

## 工作方式

### 1. 评估是否需要澄清

入口 Skill 先判断用户的想法是否缺少关键需求信息。需要澄清时进入主体对话；需求已经明确时，直接交给后续任务。

### 2. 先确认目标与边界

第一轮检查用户提出的做法是否服务于目标，并确认当前讨论范围和排除项。已有内容足够时直接核对，只有出现模糊、冲突、遗漏或隐含假设时才继续追问。

### 3. 按决策树分轮推进

AI 在内部维护需求决策树。每轮通常提出三至五个当前可以回答的问题；涉及目标、边界和重大取舍时会减少数量。依赖本轮答案的问题会留到后续轮次。

问题格式示例：

```text
❓ Q1 — 你真正希望改变什么：如果这个项目成功，当前处境会发生什么具体变化？

💭 思考提示：使用场景、当前损失、期望结果。
```

思考提示只提供思考角度，不限定答案。用户难以展开或需要比较取舍时，AI 才会提供少量候选解释或建议。

### 4. 区分不同信息状态

讨论中的内容不会被一律当作事实。`real-need` 会区分：

- **已确认需求**：可作为后续方案的约束或验收依据；
- **用户自述**：用户对自身经历或处境的描述；
- **待验证依据**：需要调查、记录、样例或实验验证的判断；
- **明确未知**：当前不知道或不愿提供，并注明其影响；
- **边界外**：不进入当前讨论的内容；
- **已排除方向**：当前不采用，并保留必要理由。

“延期”只表示处理时机，不代表某项内容已经得到验证或确认。

### 5. 输出并确认需求清单

当主目标和边界清楚，关键分支已经确认、排除或明确标记为未知、待验证、延期事项后，Skill 会生成《真实需求清单》，包括：

1. 当前问题与触发场景；
2. 目标与价值；
3. 对象与范围；
4. 成功标准；
5. 依据与未确定事项。

如果关键依据尚未验证，可以输出有条件的需求，但必须写明成立条件和影响。

最终清单需要用户明确确认。确认只代表清单准确表达了当前需求，不代表其中的事实已经验证，也不代表用户授权执行。

## 使用示例

可以直接提出尚未整理好的想法：

```text
我想建立一个个人知识库，把过去的资料都整理进去，但还没想清楚具体应该怎么做。
```

也可以明确要求先进行需求澄清：

```text
使用 real-need 帮我先想清楚这个项目真正要解决的问题，不要直接给方案。
```

入口默认提示词为：

```text
使用 $real-need 先澄清并确认这项想法的真实需求。
```

## 目录结构

```text
real-need/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
└── real-need-dialogue/
    └── SKILL.md
```

- `SKILL.md`：判断用户输入是否需要需求澄清，并路由到主体 Skill。
- `real-need-dialogue/SKILL.md`：执行分轮追问、决策树更新、信息状态管理和最终确认。
- `agents/openai.yaml`：定义 Codex 中显示的名称、简介、默认提示词和隐式调用策略。

## 安装

将整个 `real-need` 目录放入 Codex Skills 目录：

```text
~/.codex/skills/real-need/
```

安装后重新启动或刷新 Codex，使 Skill 被重新发现。入口 Skill 会根据用户表达进行触发评估，也可以通过 `$real-need` 显式调用。

## 设计边界

`real-need` 只负责需求层的澄清与确认，不负责：

- 设计技术架构；
- 编写实现步骤；
- 执行项目；
- 未经授权读取文件、工具或资料；
- 把 AI 提出的候选解释直接写成用户需求；
- 把用户确认的预测包装成已验证事实。

需要调查环境事实时，只有在用户明确要求调查或指定来源后才会进行；调查中的事实只阻塞依赖它的问题，不影响其他问题继续推进。

## 当前状态

当前版本用于实际对话验证。重点观察：

- 入口能否正确区分需求澄清与方案讨论；
- 第一轮是否能有效确认目标和边界；
- 追问是否减少重复和无关细节；
- 最终清单是否足以支持后续方案讨论；
- 是否出现过度追问、过早收敛或 AI 引导用户答案的问题。

发现问题后，应优先调整触发判断、问题选择和结束条件，避免通过不断增加规则掩盖具体对话问题。
